====================================================================
3.  THE DUPLICATE-FETCH FRACTION IS ZERO, BY CONSTRUCTION
====================================================================

Kale asked for two duplicate mechanisms.  Both are structurally excluded, and
that is a stronger answer than a small measured number would have been.

(a) SAME KEY FETCHED BY MULTIPLE PEs IN A PROCESS.  CacheManager is a
    NODEGROUP -- one branch per process, shared by all 7 PEs (`isNodeGroup()`
    at CacheManager.h:52, and the generated code uses CkSendMsgNodeBranch).
    A key fetched by one PE is in the shared cache for the other six; a second
    requester hits it or joins the pending request.  There is no per-PE cache
    to duplicate into.

(b) REFETCHED ACROSS THE WALK.  **There is no eviction path at all.**  Searching
    TreeCache.h and CacheManager.h for evict/Evict finds nothing; the only
    clearing is `destroy()` (TreeCache.h:289), which wipes the pools and
    lookups wholesale and is called between ITERATIONS.  Within one iteration
    -- and these runs are `-i 1` -- a fetched node is never dropped, so it can
    never be refetched.

CONSISTENT WITH THE COUNTS: 20,586 addCache messages per process carrying
15.5 nodes each is ~319,000 nodes, against 318,415 distinct nodes cached per
process.  About one fetch per distinct node, which is what (a) and (b) predict.

*** SO THERE IS NO DUPLICATE TRAFFIC TO REMOVE.  A "cache-fetch reduction"
    cannot come from deduplication.  It has to come from fetching FEWER
    DISTINCT NODES (better pruning, so the walk asks for less), or from
    fetching them EARLIER (prefetch, so the 28-34% of wall spent in cache
    service overlaps something), or from making each node SMALLER (214 B per
    node today; the cached-particle slimming already took one bite). ***

====================================================================
4.  THE CERTIFICATE-TOUCH FRACTION -- NOT MEASURED, AND WHAT IT NEEDS
====================================================================

This is the one part of Kale's request that neither the trace nor the existing
stats can answer.  The trace carries message counts and sizes but not KEYS, and
`cacheStats` tallies what is resident, not what was read.

*** IT IS ALSO THE MOST VALUABLE OF THE FOUR.  If a large fraction of those
    318,415 nodes per process is fetched and then never touched by a
    certificate, that is a pure pruning defect and it is exactly the "fetch
    fewer distinct nodes" lever above -- the only lever section 3 leaves open. ***

WHAT IT NEEDS: one counter per cached node (or a bit in the node), set wherever
a certificate reads it during traversal, tallied in the same post-QD sweep that
`stats()` already does (TreeCache.h:244 -- it already walks the whole cache
tree, so the tally costs nothing extra).  Report touched / cached_nodes.  That
is a small change confined to TreeCache.h plus the read sites in Traverser.h,
and it is report-only.  I have NOT written it -- it is the obvious next step
and I would rather it be agreed than guessed at.
