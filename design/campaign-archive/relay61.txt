relay61 / relay62 -- THE 5.15 s CPU REFERENCE, AND WHAT IT WAS HIDING
2026-08-21, jobs 5321505 (relay61) and 5321567 (relay62)

====================================================================
1.  THE ANSWER IN ONE PARAGRAPH
====================================================================

The 5.15 s iteration of 2026-08-18 reproduces exactly, today, on the same
machine.  There is no drift, no libfabric problem, and the environment is
not the cause.  The 5.15 s reference and every relay16+ measurement are
DIFFERENT PROBLEM SIZES.  cleanup-validate-2b-16n.sbatch passes no -l, so
it ran the FoF3 default of 12 particles per leaf; every script descended
from the GPU runbook passes "-c stats -l 128 -i 1".  One flag is the whole
2.5 s.  Chasing it further produced the useful result: -l 128 is right for
the GPU arm and badly wrong for the CPU-only arm, where leaf 32 is worth
-32.0% against the value we have been running.

====================================================================
2.  HOW IT WAS FOUND -- NO MACHINE TIME
====================================================================

Both logs were already on scratch and both print the effective config:

    5304461/rep1.log        Maximum number of particles per leaf: 12
    5320405/A-old-prod-r1   Maximum number of particles per leaf: 128

examples/fof3/Main.C, ExMain::setDefaults:
    conf.max_particles_per_leaf = 12;

"-c stats -l 128 -i 1" entered with sbatch/gpu-repro-16n.sbatch, written
2026-08-18 21:49 -- three hours AFTER the 5.15 s run at 18:54 -- copied
from Ritvik's reference job 5303289, and inherited by every script since,
including every CPU-only script.

Everything else about the two runs already agreed, which is what made the
diagnosis safe to make from the archive:

    63946 TreePieces both        decomposition 6383.7 vs 6532.4 ms
    components 424897832 both    max_size 185317566 both
    log2_histogram IDENTICAL in all 27 buckets

The whole 2510 ms sits inside the iteration and almost all of it is phaseA
(2.000 -> 4.881 s), carried in Pre-traversal (2441 -> 5213 ms).  Leaf size
does not change the FoF answer.  It changes how much brute-force pair work
phaseA does inside a leaf.

TWO FACTS CHECKED RATHER THAN ASSUMED, both against the environment
hypothesis that came in from the laptop session:

  - The LOGIN DEFAULT already loads libfabric/2.3.1.  The old binary in a
    bare login shell resolves libfabric.so.1 ->
    /opt/cray/libfabric/2.3.1/lib64.  The module block in the new scripts
    re-loads what is already there.  BUILDS.md records the production
    charm as BUILT against 1.20.1, but that is a build-time fact and does
    not describe what it loads at run time.
  - FI_MR_CACHE_MONITOR is a memory-registration setting.  The regression
    is 2.9 s of phaseA, which is local compute, not the fabric.

Both were still measured rather than dismissed.  See section 3.

4.  relay62, job 5321567 -- THE LEAF SIZE IS A REAL KNOB, BOTH WAYS
====================================================================

Production binaries, ppn 7, PEMAP7, ndev 4, poll 2, affinity fix ON, 2
reps each, all 13 runs EXACT, every arm gated on printed leaf size and on
fofgpu symbol count so a GPU binary cannot masquerade as the CPU one.

    leaf    FoF3.gpu-prod           FoF3.cpu-prod
     12    3606.9 ms  (+27.7%)     5365.3 ms  (+11.5%)
     32    3074.3     (+ 8.8%)     4811.9     BEST
    128    2825.0     BEST         7081.0     (+47.2%)

-l 128 IS CORRECT ON THE GPU.  It was never a mistake there -- it came
from Ritvik's reference run and it wins.  Leaf 12 would cost the GPU arm
28%.  The flag was only wrong where it was inherited without thought into
CPU-only scripts.

THE CPU-ONLY HEADLINE IMPROVES BY 32.0%, from 7081.0 to 4811.9 ms, from
one flag.  The cpu-l32 reps landed 0.5 ms apart.  Note this also beats the
5.15 s reference everyone was trying to recover: leaf 12 was not optimal
either, it was merely closer than 128.

THE MECHANISM, from rep 1 of each arm:

              CPU phaseA   CPU Pre-trav   GPU phaseA   GPU Pre-trav
    leaf  12    2.540 s      2941 ms      0.000 (dev)    1089 ms
    leaf  32    2.378        2709         0.000           989
    leaf 128    4.575        4871         0.000           797

On CPU phaseA is host union-find and a large leaf costs brute-force pair
work inside the leaf.  On GPU phase1 runs on the device (FOF_GPU_PHASE1=1,
so phaseA reads 0.000) and a larger leaf is a bigger, better-shaped unit
of device work.  The two arms want opposite things for a reason.

The GPU Pre-traversal is STILL FALLING at 128, which is the one thing this
sweep did not settle: 128 was the largest value tried and won, so it may
be the edge of the range rather than a maximum.  relay63 (job 5321648)
pushes GPU to 192/256/384 and brackets the CPU interior minimum with
16/24/32/48/64.  PENDING -- see section 6.

5.  CORRECTIONS
====================================================================

  - The laptop session's SCRIPT LINEAGE instinct was right and the two
    candidate carriers it named were both wrong.  The carrier is an app
    argument, not the environment.

  - MINE, from relay49/relay59.  Arm A0 was specified as "the same binary
    and runtime with NO FOF_* set at all, i.e. its own defaults, so A0 vs
    A separates the configuration changed from the machine drifted."  It
    only unset the FOF_* ENVIRONMENT.  It kept -l 128 on the command line.
    It was never the control it claimed to be, and its 9644.6 ms is not
    "the old defaults".

  - RESUME.md said "Prime suspect: libfabric (production charm was built
    against 1.20.1, every job here loads 2.3.1).  NEXT JOB IS ONE ARM: arm
    A with libfabric/1.20.1."  That job is no longer worth running.  The
    08-18 run ALSO loaded 2.3.1 -- it is the login default and always was
    -- so there is no version difference between the two dates to test.

  - "Until then 5.15 s is not a usable baseline" is now resolved: it is a
    usable baseline FOR LEAF 12, and it should never be compared against a
    leaf-128 number again.
