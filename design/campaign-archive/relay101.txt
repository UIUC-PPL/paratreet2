PREDICTION CONFIRMED.  The script put on record, before the run, that capping
should win by MORE on GPU than on CPU, because loadCache is HOST-side work
that the device path does not touch while the GPU arm roughly halves the
iteration.  Measured: loadCache uncapped is 396 ms of a 1372 ms iteration --
28.9%.  On CPU at 128 nodes the best cap was worth -14% to -23% (relay93/94);

from 0 to 323,747.  On the GPU path the lazy canopy refill is essentially
free, which is the opposite of the CPU picture where capping cost the walk
30-140 ms.  That is why the GPU crossover is so much more favourable, and it
is the part of this result I would most want a second rep to confirm.

====================================================================
4.  THE DIAGNOSIS.  IT IS THE SBATCH HEADER, NOT THE GPU.
====================================================================
Chased over three jobs.  Every hypothesis I offered was wrong until the last.

relay103 (5334873), a 2x2 of CPU/GPU against helper pinning:
  A cpu  978 s   C gpu 1401 s      (labelled "helpers off" -- SEE THE
  B cpu 1015 s   D gpu 1216 s       CORRECTION BELOW; they were not off)
ALL FOUR SLOW.  Not the GPU codepath, not FOF_HELPER_CPUS.

CORRECTION TO MY OWN LABELS.  I called the A/C cells "helpers off".  They
were not.  Unsetting FOF_HELPER_CPUS leaves the built-in affinity fix ACTIVE
in its SMT-SIBLING form, because FOF_NO_AFFINITY_FIX was never set.  So
relay103 compared CCD-FIRST pinning against SMT-SIBLING pinning:
    CPU  ccd-first 1737 ms  vs  smt-sibling 1745 ms   0.5% better
    GPU  ccd-first  969 ms  vs  smt-sibling 1015 ms   4.5% better
The CCD-first variant DOES help the iteration, and more on GPU than on CPU.
It simply cannot pay for ~1100 s of startup at 128 nodes.
THE GENUINE NO-FIX ARM (FOF_NO_AFFINITY_FIX=1) HAS NEVER BEEN RUN AT 128
NODES, so the case the fix exists for -- a ROCm helper occupying a whole PE
through the treewalk -- is still unmeasured at this scale.
AND THAT 2x2 WAS WEAKER THAN I DESCRIBED IT.  The core-thief fix is TWO
things -- an ALLOCATION (--core-spec=0 --cpus-per-task=16) and an ENV VAR
(FOF_HELPER_CPUS).  The allocation half is set in the sbatch header, so it was
present in all four cells; I varied only the env var.  It excluded two things
and nothing else.

relay104 (5335196), a ladder from the known-good configuration:
  A v89main l32  pmi 4M    49 s FAST   (reproduces relay97/99)
  B v89main l32  pmi 16M   26 s FAST   -> PMI_MAX_KVS_ENTRIES is not it
  C v89main l128 pmi 4M    29 s FAST   -> the leaf is not it
  D v91cpu  l32  pmi 4M    31 s FAST   -> the b0f04fc binary is not it
  E v91cpu  l128 pmi 16M   32 s FAST   -> nor all three together
ALL FIVE FAST.  The machine is not it either: A reproduced 49 s at 22:53, and
a direct Lustre probe from the login node gave 3.3 GB/s single-stream across
three offsets with the project queue empty.  The Ritvik-congestion story I
floated on timing alone is dead.

WHAT IS LEFT is the one variable neither job could vary, because it lives in
the sbatch header rather than the srun line: --core-spec=0 --cpus-per-task=16.
relay103 had it in every cell (all slow); relay104 in none (all fast).  It is
the only difference between relay104-E at 32 s and relay103-A at 978 s.
Job 5335233 (relay105) carries that header with relay104-A's otherwise
known-good configuration, and separates the cpuset width from --core-spec by
running one arm at srun --cpus-per-task=14 inside the same allocation.

IF CONFIRMED, IT REACHES PAST THIS JOB.  The campaign records the core-thief
fix as -22.8% at ppn 7 -- MEASURED AT 16 NODES.  Nothing has checked its cost
at 128.  Every relay script has printed a per-rep seconds column and I read it
as harmless launch overhead: 27-50 s on CPU, and nobody asked why it was 27-50
and not 5.  At 1274 s it stopped being ignorable.  relay103 was the first
report in this campaign to print wall-minus-iteration at all.

WHAT IT DOES NOT TOUCH.  Section 1 stands unchanged.  Every arm inside
relay101 saw the same machine and the same header, so the -35.9% and the
