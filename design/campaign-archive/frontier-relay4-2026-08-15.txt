1. THE SPEC ASKED FOR AN A/B WHOSE TREATMENT ARM CANNOT PASS ITS OWN GATE
====================================================================
   Expected: every arm returns components 424897832; a mismatch is a
   stop-and-report event.
   Found:    -march=znver3 returns 424897833 -- one component OVER gold --
             reproducibly, 6 arms out of 6 across two jobs. -Ofast likewise,
             0/6 exact, same +1.
   Cause:    gcc defaults to -ffp-contract=fast. SSE2 has no FMA instruction,
             so the base binary physically CANNOT fuse a*b+c; znver3 makes FMA
             available and gcc starts using it, which changes the rounding of
             the linking-length distance test. A pair on the boundary falls the
             other way.
   Fix:      -march=znver3 -ffp-contract=off is EXACT 6/6 and keeps 5479 of the
             5540 vector references (all 69 FMAs go, nothing else does).
   Note:     this is not a code bug. Both counts are defensible float answers.
             But the gate as written is unsatisfiable by the experiment as
             specified, so the spec needed the extra flag to be runnable at all.
   Cost:     job 5273921 aborted 10 of its 12 arms on this, including the whole
             pool sweep, which uses the BASE binary and could not have been
             affected. Hence three jobs instead of the "one 2B/16-node job" the
             prompt planned.

2. THE "PROOF THE KNOB TOOK" LINE DOES NOT EXIST
====================================================================
   Expected: 'The binary prints the effective value once at startup:
             PARATREET pool_elem_size: N nodes (K KB/chunk) -- check it in
             every arm's output, it is the proof the knob took.'
   Found:    it prints on NO process, in any arm. The string is in the binary.
             The guard is `if (CkMyPe() == 0)` inside CacheManager::initialize,
             and src/paratreet.ci declares `nodegroup CacheManager` (GROUP_CACHE
             is not defined in any makefile). A nodegroup branch entry method
             can be delivered to any PE of the process, and on process 0 it did
             not land on PE 0. Nothing appears between "* Initializing cache
             managers." and "* Initialization".
   Impact:   anyone following the spec literally would conclude the knob did
             not take. It did.
   Substitute used: `FOF3STAT cache: pool_MB` (= chunks x pool_elem_size x
             sizeof(FullNode), i.e. allocated capacity). It moves monotonically
             with the knob and the two default arms agree to 0.003%. It is a
             better instrument than the intended print.
   Fix:      guard on CkMyNode()==0 && CkMyRank()==0, or print from Driver.

4. THE CHUNK-WASTE MODEL IN THE SPEC IS OVER-STATED
====================================================================
   Expected: 'Chunks are allocated whole, so large values waste up to one chunk
             per lane per piece-tail.'
   Found:    FullNodePool (src/TreeCache.h) is a bump allocator over a LIST of
             chunks, and the next piece continues in the current chunk. So the
             waste is at most one partial chunk PER POOL, not per piece.
   Measured: pool bytes +0.4% at 4096, +1.6% at 16384, +6.1% at 65536
             (1890.5 -> 2004.9 MB/process). Not the multiple the per-piece
             reading implies.
   Bearing:  the same structure explains why the sweep is a null (item 7): a
             piece's nodes were ALREADY bump-allocated in preorder within its
             chunks; the knob only removes a boundary every 128 nodes.

6. charmc MIS-PARSES `-march=X -Ofast` IN THAT ORDER
====================================================================
   Not anticipated anywhere in the spec.
     charmc ... -march=znver3 -Ofast -c x.C -o x.o
       -> cc1plus: error: bad value 'znver3 -Ofast' for '-march=' switch
   The two tokens reach cc1plus joined into the -march= value. Reversing them
   (-Ofast -march=znver3) works and is how the fast binary was built. The error
   names -march= and sends you hunting for an unsupported architecture, which
   is not the problem. Worth a line in the build notes.
   (znver3 itself IS accepted by the Cray wrapper -- gcc 13.3.1 -- so the
   -march=native fallback the prompt offered was never needed.)

7. THE RESULT ITSELF: SIMD IS HALF THE WIN THE PROMPT HOPED FOR
====================================================================
   Expected: 'the hot phaseA/phaseB inner loops are float distance tests, so
             this is potentially large, or potentially zero.'
   Found (6 reps base/march3/fast, jobs 5273936+5273967, paired wins in
   brackets):
             -march=znver3 -ffp-contract=off  (EXACT 6/6)
                phaseA    -3.5%  [6/6]   <- real, consistent
                phaseB    +0.1%  [3/6]   <- nothing
                phase1    -2.0%  [3/6]   <- inside base's own spread
                Iter0     -0.9%  [3/6]   <- nothing
             -Ofast -march=znver3  (NOT EXACT 0/6)
                phaseA   -12.8%  [6/6]
                phaseB    -3.0%  [5/6]
                phase1    -8.1%  [6/6]
                Iter0     -4.0%  [6/6]
   So: the exact form of SIMD gives a genuine but SMALL phaseA win that does
   not survive to Iteration 0. The large win is real and repeatable but it
   belongs to -ffast-math, not to vectorisation, and it costs bit-exactness.
   phaseB -- the straggler, the thing the campaign is chasing -- does not move
   under either.
   OPEN, and cheap: most of -Ofast's extra may come from -fno-math-errno
   (semantically safe -- it only stops gcc preserving errno on sqrt) rather
   than from reassociation. One more 12-arm job would separate them and could
   plausibly recover much of the 4% Iter0 EXACTLY. Not run -- say the word.
