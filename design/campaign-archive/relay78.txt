1.  THE PROTOCOL, AND WHAT WAS COUNTED
====================================================================

union_request(v,w) -> find_boss1 on v carrying partner w
  find_boss1  parent != -1 : climb (local while-loop, or ONE remote message)
              parent == -1 : root of v found; send find_boss2 to w
  find_boss2  parent != -1 : climb
              parent == -1 and boss1ID >  self : FLIP -- re-issues
                             union_request and throws the chain away
              parent == -1 and boss1ID <  self : UNION.  sets parent, starts
                             an add_size chain that climbs to the root
              parent == -1 and boss1ID == self : SAME ROOT.  does nothing

Counters at every one of those branch points, summed over the array and
printed as [UFSTAT].  AGGREGATION is off in our build, so each remote hop is
a real message.  The UnionFindLib array has 128 elements, one per process.

Kale: "If it is not long chains (and is mostly discards), we may be better

6.  KALE WAS RIGHT ABOUT THE PARTIAL ORDER.  MY GUARD IS SOUND, MY
    JUSTIFICATION FOR IT WAS NOT.
====================================================================

Kale: "'parent ids decrease' is a partial order.  I don't think it implies
equivalence between 'closer to root' and 'smaller'."

Correct, and my §4 wording was wrong.

WHAT IS ACTUALLY TRUE.  Every site that assigns a parent gives the vertex a
STRICTLY SMALLER id -- verified at all five: find_boss2's union branch (guarded
by boss1ID < src->vertexID, else it flips), anchor (":v will be smaller here"),
local_union's two direct branches (unionFindLib.C:655-660, which order tip1
against tip2 first), and local_path_compression (a tip is always an ancestor).
So along ANY ONE root path ids strictly decrease.

WHY THAT DOES NOT GIVE THE EQUIVALENCE.  Id order is total; ancestry is
partial.  Two vertices can be id-comparable with neither an ancestor of the
other.  My argument silently assumed the proposed G and the current parent P'
both lie on src's CURRENT root path.  That fails exactly under path
compression: if src's pointer has already jumped over G, then G is no longer on
src's path at all, and "which is closer to the root" is not even defined for
the pair.  So "the guard never moves the pointer away from the root" is NOT a
theorem.  Kale's objection is right as stated.

*** THE GUARD IS STILL SAFE, FOR TWO SIMPLER REASONS THAT DO NOT NEED THE
    EQUIVALENCE.

    (a) NO CYCLE.  By the min-heap invariant every descendant of src has a
        strictly LARGER id than src.  The offered G has a smaller id than src
        (it was an ancestor when the message was built).  So G can never be a
        descendant of src, and pointing src at G cannot close a cycle.  This is
        the property the existing CkAssert was groping at.

    (b) RIGHT COMPONENT.  G was in src's tree when the message was built, and
        trees only ever MERGE, never split.  So G is still in src's tree and
        following G's parents still reaches the root src should reach.  Labels
        stay correct even if G is off src's current path.

    (c) WHAT THE COMPARISON ACTUALLY BUYS is not "closer to the root" but a
        strictly DECREASING id on each accepted write.  That is a well-founded
        measure, so accepted updates cannot oscillate or livelock.  Progress,
        not distance. ***

CONSEQUENCE FOR THE §4 READING.  I described the 94% rejected offers as
"already matched or beaten".  That is stronger than the data supports.  The
honest statement is: 94% of offers did not carry a strictly smaller parent id
than the one already installed.  That is consistent with the sender having
been compressed further already, but it does not prove it.

All arms EXACT with the short-circuit on is evidence the guard is not breaking
anything, and it is only evidence, not proof.

7.  WHAT add_size DOES, AND WHY THE ALGORITHM NEEDS IT
====================================================================

WHAT.  add_size(v, delta) adds delta to the size of the ROOT reachable from v.
If v is not a root it forwards to v's current parent -- recursively, by remote
message when the parent is off-chare.  So it is a second pointer-chasing climb,
running concurrently with the find chains.

WHERE IT IS CALLED.  Only at a union, and always just BEFORE the parent write:
find_boss2:407-412, anchor:541-546, and inline in local_union:656-659.  The
merging root src was a root, so src->size is its whole subtree count, and that
count is handed to the surviving root.

WHY IT MUST FORWARD RATHER THAN JUST WRITE.  Between find_boss2 observing that
boss1 was a root and the add_size landing there, boss1 may itself have been
merged under some other root.  A plain write would strand the count on a
non-root, where nothing would ever read it, and the component size would come
out short.  Forwarding makes the delta land at whatever the CURRENT root is.
The comment at unionFindLib.C:721 says exactly this.

WHY IT IS EXACTLY-ONCE, which is the part that makes the whole thing correct.
The size transfer and the parent write happen inside ONE entry-method
execution, and Charm entry methods on a chare are non-preemptive.  So any other
add_size aimed at src is processed strictly before or strictly after, never
interleaved:
    processed BEFORE : its delta is already inside src->size and is carried
                       along by the transfer.
    processed AFTER  : src now has a parent, so it forwards upward.
Either ordering counts every vertex exactly once.

THE INVARIANT, PLAINLY.  A vertex's size field is meaningful ONLY while it is a
root.  Once it has a parent the field is dead -- its contribution has already
been passed up -- and every later delta bypasses it by forwarding.  The sum of
size over roots is therefore invariant and equals the vertex count.

WHAT CONSUMES IT.  set_component(i, componentNumber, size) at :1042 delivers
the label together with its size; the app reports max_size (our EXACT gate
value 185,317,566) and prune_components uses it.  So a lost or double-counted
delta breaks the gate immediately.  Every arm in relay74-78 being EXACT is a
real check on all of the above, not a formality.

MEASURED.  41,377 of 479,445 add_size calls (8.6%) had to forward, i.e. the
root had moved under them.  Average add_size chain 1.09 hops.  So the
"root moved" race is real at about one in twelve.

8.  ACIC AS THE TRIGGER -- and the one number that reshapes the design
====================================================================

Kale: "The moment has to be after the treewalk is completely finished (or else
new edges will trickle in).  An asynchronous reduction (every PE contributing
when it is done with all its treewalks, even though it can still respond to
others' requests with addCache) will help identify that. ... broadcast /
async reduction / delay-at-root / broadcast cycles (ACIC).  The reductions
collect remaining edges not yet submitted.  The question of unions in flight
has to be dealt with."

THIS IS THE RIGHT SHAPE AND IT SOLVES WHAT KILLED THE WAVE.  The wave needed a
moment defined on the CASCADE, which has no local completion predicate -- no PE
can know the cascade is nearly done.  "I have finished my own tree walks" IS
locally decidable, so a reduction can detect it, and serving addCache after
contributing is exactly right because cache service is not edge-producing.

*** BUT THE EDGES ARE ALREADY IN.  union_requests batch messages: 73,365 during
    the walk against 4,000 after the walk is 99% done -- about 5%.  At -E 16
    that is ~1.24M edges submitted, and essentially all of them are submitted
    before the drain begins.  So a reduction that collects "remaining edges not
    yet submitted" would collect almost nothing.  What is left in the drain is
    the CASCADE of already-submitted edges, not unsent edges. ***

That reframes the payload, and it splits the design in two:

OPTION 1 -- DO NOT STREAM THE BOUNDARY EDGES AT ALL; GATHER THEM.
  Then nothing is ever in flight, by construction, and the in-flight question
  disappears instead of being solved.  The volumes say it is tractable:
      distinct cross-chare edges   ~453,000   (543,048 chains minus the
                                               89,865 flips, which are
                                               re-issues of the same edge)
      vertices they touch          <= ~906,000
      as a contracted graph        ~7 MB
  A sequential union-find over 453k edges is a few milliseconds.  The
  same-chare fast path (794,192 local_unions) stays where it is and only its
  local ROOTS enter the gather.
  COST: the streaming overlap, measured at 104 ms (relay76, E0 - E16).
  GAIN: the whole distributed protocol -- 265 ms of drain and 4,310 PE-ms --
  becomes gather + sequential pass + one broadcast of the root remapping.
  ON PAPER that is net 150-200 ms, 3-4% of the CPU iteration, AND it removes
  the 16.5% flips for free, because whatever finishes centrally holds BOTH
  roots and orders them once.  NOT MEASURED -- this is arithmetic, not a run.

OPTION 2 -- KEEP STREAMING, MOP UP WITH ACIC.
  Then in-flight unions must be handled, and ACIC already gives the rounds.
  Have each PE contribute (union_messages_sent, union_messages_received) in the
  same reduction.  If the two global totals are EQUAL in a round and no PE did
  union work since the previous round, nothing is in flight.  That is Mattern's
  four-counter method: two consecutive consistent rounds, no runtime-wide
  quiescence needed.  The library already has increase_message_count() hooks
  under #ifdef PROFILING, so the counting points exist.

  THE HARD PART OF OPTION 2, and it is a real one: to collect mid-cascade you
  must know WHICH edges are still unresolved, and the library does not track
  that -- an edge is forgotten the instant its find_boss1 is sent.  Mid-cascade
  collection therefore needs new per-chare bookkeeping (an outstanding-edge set,
  retired on union / discard / flip).  Option 1 needs none of it.

MY READING: option 1 is the one the numbers favour, and it is also the smaller
change.  The 104 ms of lost overlap is a known, already-measured price; the
265 ms drain and the flips are the return.  Option 2 keeps the overlap but buys
the in-flight problem and the bookkeeping with it.

NOT MEASURED and worth stating: whether the gather itself scales -- 453k edges
is one reduction, but the broadcast of the remapping is up to ~906k entries,
and neither has been timed at 16 nodes.

Kale: "Isn't there another pass at the end for finding sizes via a custom

There is, and it is the ONLY one that is read.  The evidence chain, all of it

  2. The library maintains it at every union through add_size, forwarding to

  3. find_components -> set_component propagates BOTH componentNumber and

  4. *** THE APP READS BACK LABELS ONLY.  collectComponentLabels

         for (auto& kv : lazy_store) out[kv.first] = kv.second.componentNumber;
     and lazy mode is on by construction -- unionFindInitOnePerNode broadcasts
     enableLazyMode before `ready` fires (unionFindLib.C:1451). ***
  5. componentSize appears EXACTLY ONCE in the whole app: FoFPhase1.h:1144
     "v.componentSize = -1;".  It is never read.
  6. The app never calls prune_components, return_vertices/get_vertices, or

  7. The library's size-consuming path -- merge_count_results plus the custom

  8. The app computes sizes ITSELF at the end, from the labels, exactly as
     Kale described:
         depositLabelCounts
         -> histogramShard   (tuple reduction: bins, n_components, MAX_SIZE)
         -> collectTouchedCounts (cross-process sum over the TOUCHED,
            i.e. non-local, components only; bins and max_size recomputed
            from those pairs, FoFPhase1.h:4813-4836)

*** SO max_size -- OUR EXACT GATE VALUE 185,317,566 -- COMES FROM THE LABEL
    HISTOGRAM, NOT FROM THE LIBRARY'S size.  add_size maintains a quantity
    that nothing in this application reads. ***

WHAT IT COSTS, from the relay78 census and the traces:
    add_size calls per run                 479,445
      of which forwarding hops              41,377   (8.6%)
    add_size executions in the 265 ms drain 145,129
      of 476,945 drain protocol messages     30.4%

So roughly THIRTY PERCENT of the drain's message traffic maintains a dead
field.  This is the cheapest candidate on the table: it REMOVES work instead
of adding a mechanism, and it needs no trigger -- which is precisely what
killed the wave.

HONEST CAVEATS, because this is not automatically a win:
  - add_size is NOT on the find dependence chain.  It is fire-and-forget,
    issued just before the parent write, and nothing waits on it.  In a
    latency-bound drain the length is set by the longest dependence chain, so
    removing a side flow need not shorten it.
  - But Charm entry methods are non-preemptive: every add_size execution
    delays whatever find message is queued behind it on that PE, and only
    ~39 PEs are active in the drain.  Whether that queuing matters is exactly
    what a measurement would settle.
  - The library is shared.  Removing add_size outright would break any client
    that DOES read sizes (dense mode, prune_components).  The right form is a
    knob, and the library already has the lazy/dense split to hang one on.
  - local_union also does a direct "size +=" (unionFindLib.C:656-659).  Those
    are local and harmless; a no-sizes mode can leave them or skip them.

COST TO FIND OUT: one env knob in the library, one production build, one
16-node job with two arms.  About ten minutes of machine time.  Not run --
Kale has not asked for it.
