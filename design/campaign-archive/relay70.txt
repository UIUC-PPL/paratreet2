3.  THE DENSE HISTOGRAM
====================================================================

    arm                          component_histogram    Iter0
    OLD binary, leaf 32                   0.429 s      4875 ms
    NEW hash,   leaf 32                   0.497 s      4836 ms  (relay70 arm 2)
    NEW hash,   leaf 128                  0.500 s      7222 ms
    NEW DENSE,  leaf 32                   5.500 s      9795 ms
    NEW DENSE,  leaf 128                  5.479 s     12148 ms

Dense is 11x the hash path and DOUBLES the CPU iteration.  The brief
expected the ~280 ms row to fall to tens of ms; the hash row is 497 ms here
and dense takes it to 5.5 s.  The local 1M result (5-6 ms against 20-42 ms)
does not carry to 2B.

LIKELY MECHANISM, from the code rather than from a profile.
`ensureDenseHist` sizes the array from the PROCESS'S WHOLE PARTICLE ORDER
RANGE: width = order_hi - order_lo + 1.  At 2B over 128 processes that is
~15.5M std::atomic<long> per process, ~124 MB, allocated with new[] and
then zeroed in a SINGLE-THREADED loop under label_shards_init_lock, and
scanned again on the read side.  The cost is proportional to the order
RANGE, not to the number of labels -- so it grows with the problem while
the hash path grows with the (far smaller) label count.  At 1M the range is
small and dense wins; at 2B the range is the whole process.

DENSE AND HASH ARE EXACTLY EQUIVALENT.  The full FOF3STAT components line
is BITWISE IDENTICAL between the dense and hash arms -- 277 bytes, 33
fields, every bin.  They are equally wrong, but the two paths agree
perfectly, so the dense implementation itself is faithful to the hash one.

4.  THE DENSE + GPU ABORT
====================================================================

    Assertion "order >= nb->dense_lo && order < nb->dense_lo + nb->dense_width"
    failed in fof/FoFPhase1.h line 3705        (rc 134, many tasks)

    dense + GPU   ABORTS        (relay70 arm 3)
    dense + CPU   runs clean    (relay71 arm D, leaf 128 -- same leaf size)
    hash  + GPU   runs clean    (relay71 arm E)

So it is the COMBINATION, not the leaf size and not the GPU path alone.

The dense path assumes a positive (untouched) label's low 43 bits are a
global order INSIDE THIS PROCESS'S SFC range.  Under the GPU phase-1 path
that assumption does not hold: some positive label carries an order outside
[dense_lo, dense_lo+dense_width).  Given that the prefix removal changes
bosses to self-name with their vertexID, a component whose boss lives on
another process is the obvious candidate -- which would make this the same
root cause as section 2, seen through a different assertion.
