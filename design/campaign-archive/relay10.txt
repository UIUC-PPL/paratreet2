13. WHY CONCAT.  Driver::shedPlan must issue the migrations (issuing them
    inside the broadcast is the fb43f06 crash), so the plan has to reach the
    Driver, and across a chare array the only gather is a reduction; concat
    rather than sum/max because the payload is a variable-length LIST of
    records.  The same reduction is also the barrier -- it completes only
    after every element got the broadcast.  The mechanism was right; the
    DENOMINATOR was wrong (non-candidates had no reason to send bytes).

17. RANKING IS IMPLEMENTED -- patches/0010, bin/FoF3.2b.shedrank,
    md5 8f47b65b927b660bcf4f403b5819ed33, TraceSummary 0, vfmadd 0,
    "SHED rank" string present.  The CHOICE moves from the element to the
    Driver: each piece on the victim contributes (index, n, score) and
    Driver::shedPlan sorts and takes the top k, ties broken by index so the
    plan is reproducible.  FOF_SHED_RANK: 0 = -index (blind, deterministic,
    = shed from the low end of the SFC run, THE CONTROL), 1 = n^2/V^(4/3)
    (work per piece), 2 = n/V^(4/3) (work per PARTICLE, the cost/benefit
    ratio), 3 = 1/V^(2/3) (per-particle with the sqrt-compressed term).
    FOF_SHED_DESTS spreads over d destination processes, default 1 = the
    old single destination, left at 1 so this job isolates ranking.
    Same reduction, same barrier, every element still contributes.
    Determinism is part of the readout: the new "SHED rank:" line prints
    particles_moved and the top/cut scores, which must be IDENTICAL across
    reps if ranking works -- and that is the property that makes a later
    projections capture meaningful at all.
    NIT to tighten before it lands: ShedCand is left default-initialised on
    non-candidates and passed with length 0.  Safe (nothing reads it) but it
    should be `ShedCand c{}`; not changed here because the binary that
    produced the results was already built.
