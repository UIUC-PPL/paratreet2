WHAT THIS RETRACTS -- and it is a real retraction, not a footnote

11. design/walk-uf2-overlap.md step (1) recorded a 2B A/B of -E 0 vs
    -E 4096 (job 19582087, Anvil, pre-split), found walk+uf2 4.65/4.52 vs
    4.67/4.67, and concluded "performance-neutral".  THAT A/B DID NOT RUN
    THE EXPERIMENT.  At ~970k edges over ~1920 PEs the per-PE yield was
    ~505, so -E 4096 never flushed mid-walk either -- it compared
    no-overlap against no-overlap.  The null is an artifact of the batch
    size, not a property of the mechanism.

12. THE DIAGNOSIS BUILT ON THAT NULL IS ALSO WRONG at these edge volumes.
    The doc concluded the uf2 wall "sits in what runs AFTER all unions --
    find_components' own serial latency structure ... which no amount of
    union overlap can touch by design".  Now measured directly: at -E 16
    the uf2 bracket (remainder flush + QD + find_components) is 0.071 s.
    So find_components' serial structure is ~0.07 s, not 0.65 s.  The
    other 0.6 s was union injection and its cascades, and it overlaps.
    The "sparse-message-latency disease, not an application-schedulable
    cost" reading does not survive.

13. The doc's verdict line "KEPT with default -E 4096: zero measured cost"
    is literally true and badly misleading.  4096 is not a conservative
    default, it is an off switch.


RECOMMENDATION AND THE GAP

14. *** SUPERSEDED BY ITEM 20 BELOW -- 512 IS REFUTED AT 64 NODES.
        The original text is kept so the wrong reasoning is visible. ***
    RECOMMEND changing the default from 4096 to 512.  512 and 16 measure
    the same; 512 is the conservative end of the tie -- 32x fewer messages
    than 16, a useful peak_edge_buf bound, and margin before an overhead
    floor this sweep did not find.  The default lives in
    examples/fof3/Main.h:82.  No code change needed to USE it, and I have
    not made one.

15. *** CLOSED -- the 64-node job ran, see items 17-21. ***
    THE GAP, and I did not close it because the task said 16 nodes:
    this is 16-node data only.  The campaign's operating point is 64 nodes
    (2771 ms, the best absolute result), and that is where it matters most
    in relative terms -- at 64 nodes uf2 is 0.723 s of a 2771 ms iteration
    = 26%, against 12% here.  If the same ~0.6 s of the bracket is
    injection rather than find_components at that scale, the effect on the
    headline is several times the 3.8% measured here.  Nothing in the
    mechanism says it should fail at 64 nodes and nothing measured says it
    holds.  I would not land a default change on 16-node data.
    ONE SHORT JOB CLOSES IT: 64 nodes, arms -E 0 / 4096 / 512 / 16, two
    reps, ~3 minutes of allocation.  Say the word and I will run it.

16. Second, smaller caveat: 924 edges/PE is a POST-SPLIT number (the split
    inflates edges 3.4x; the unsplit run is 491,173 = 274/PE).  So any -E
    default has to be stated as a default FOR THE SPLIT CONFIGURATION.  On
    an unsplit run the batch would have to be smaller still to trigger at

17. YOUR PREMISE IS CONFIRMED, AND JOB 5288946 ALREADY HELD THE PROOF.
    peak_edge_buf on the default -E 4096, read out of the scaling job:

       nodes   PEs     edges      per PE   max per PE   does 4096 fire?
        16    1792   1,655,535     924       6453       once, one PE
        64    7168   2,903,750     405       3465       NEVER
       128   14336   3,815,309     266       2307       NEVER

    Total edges rise with node count, per-PE yield FALLS -- exactly as you
    said.  The default has never fired at 64 or 128 nodes in ANY run this
    campaign has made.  512 is also above the per-PE mean at 64 and 128, so
    512 is not scale-safe either.

18. THE 16-NODE WIN DOES NOT SCALE.  Means of two reps at 64 nodes:

       -E      walk    uf2   walk+uf2   Iter0      d(Iter0)
        0     0.235  0.734     0.969   2759.7        --
        4096  0.251  0.708     0.959   2763.8      +4.1  (+0.1%)
        512   0.508  0.559     1.067   2864.2    +104.5  (+3.8%)  WORSE
        16    0.868  0.076     0.945   2736.7     -23.1  (-0.8%)  noise

    -E 512 is WORSE THAN DOING NOTHING at 64 nodes: both its reps are
    slower than every other rep in the job, against a ~60 ms within-arm
    spread.  -E 16 moves the work exactly as at 16 nodes (walk +0.633,
    uf2 -0.658) but the two now CANCEL: -23 ms is inside the rep spread.

19. WHY, and it is not a failure of the mechanism.  What disappeared is the
    slack it was hiding in.  At 16 nodes the walk is 0.352 s and can absorb
    0.21 s of union work for free.  At 64 nodes the walk is 0.235 s -- it
    shrank with the node count -- while total edges GREW 1.66M -> 2.90M.
    More union work, less walk to hide it under, so moving it in is close
    to a pure transfer.
    The corrected rule for anything else in this campaign that proposes to
    overlap X with Y: THE CEILING IS Y's IDLE TIME, NOT X's COST.  My
    section-8 worry had this backwards -- I argued the prize would be
    BIGGER at 64 nodes because uf2's share of the iteration is 26% there
    against 12% at 16.  uf2's share did grow; the walk's slack shrank more.

20. RECOMMENDATION, CORRECTED: DEFAULT 16, which is what you said.
    You were right, though for a reason neither of us had: not only does
    512 fail to fire at scale, it is an active REGRESSION where it does
    fire.  16 is the only value measured never worse:

                        16 nodes            64 nodes
       -E 4096 (today)  baseline            baseline
       -E 512           -208 ms (-3.8%)     +104 ms (+3.8%)
       -E 16            -208 ms (-3.8%)     -23 ms (-0.8%, noise)

    16 is also the only value whose behaviour does not depend on scale:
    per-PE yield is 266-924 across 16-128 nodes, so a 16-edge batch fires
    everywhere at every size.  A default that quietly turns itself off as
    the machine grows is the exact trap this investigation uncovered, and
    512 repeats it one scale later.
    Change examples/fof3/Main.h:82 from 4096 to 16.  Still not landed here
    -- Frontier does not push, and this needs no patch from me if you make
    the one-line change on the laptop.

21. STATE IT HONESTLY WHEN YOU LAND IT: this is a 16-node win that is FREE
