1.  THE ANSWER TO THE QUESTION ASKED
====================================================================
"If the collect gate is worth ~130 ms at 64 nodes too, 64 nodes turns from a
tie into a capping win and the crossover moves down."

IT IS NOT WORTH ~130 ms AT 64 NODES.  It is worth 42 ms at -s 128 and
nothing at -s 2048.

  arm                    Iter0 ms   [range]              vs uncapped
  MU + GU  uncapped n=2   1810.4    [1806.6..1814.2]        --
  M128  main  -s 128 n=3  1750.2    [1716.8..1796.9]      -60.2
  G128  gate  -s 128 n=3  1708.2    [1691.1..1733.1]     -102.2
  M2048 main  -s 2048 n=2 1710.3    [1705.0..1715.6]     -100.1
  G2048 gate  -s 2048 n=2 1717.4    [1682.9..1751.9]      -93.0

  THE GATE'S OWN CONTRIBUTION (G - M, same cap, paired, order alternated)
   -s 128    rep1  -3.8   rep2  -25.7   rep3  -96.5    mean  -42.0 ms  -2.4%
             G faster 3 of 3, BUT THE RANGES OVERLAP
             (G's worst 1733.1 is above M's best 1716.8)
   -s 2048   rep1 -22.1   rep2  +36.3                  mean   +7.1 ms
             no effect, wrong sign, n=2

  MECHANISM, unambiguous either way:
   -s 128    raw_canopies 35,388 -> 1,170   sort_s 4.47 -> 0.10 ms
             loadCache 8.0 -> 3.0 ms
   -s 2048   raw_canopies 35,388 -> 6,754   sort_s 4.40 -> 0.90 ms
             loadCache 15.0 -> 12.0 ms

WHY LESS THAN AT 128 NODES.  The collect is 35,388 messages here against
69,670 there -- half the messages, but the gain falls from 134.8 to 42.0 ms,
a factor of 3.2.  The cost of the serial fan-in grows faster than the message
count, which is the same anti-scaling relay92 measured for loadCache overall.
That is consistent, and it means the gate is worth MORE at 256 and 512 nodes
than either measurement here, not less.

CONCLUSION FOR THE CROSSOVER.  The gate does NOT move the crossover much at
64 nodes, because in this allocation capping ALREADY wins without it
(-60.2 ms), and the gate adds a smaller second increment.  The advice for 24B
should rest on the 128-node trend and on section 3 below, not on this 42 ms.

====================================================================
2.  MY WHOLE-LEVELS ARITHMETIC WAS WRONG.  THE RUN GATE CAUGHT IT.
====================================================================
I predicted the -s 2048 collect would be 9,362 raw.  It is 6,754.  The gate
I wrote into the script fired on every G2048 rep:

  !!! GATE ARM collected 6754, whole-levels predicts 9362

The code is correct; my prediction was not.  I computed the kept level count
from a COMPLETE tree: -s 2048 -> want 14,337 -> limit 32,768 -> depths 0..4
= 1+8+64+512+4096 = 4,681 elements.  THE CANOPY IS NOT COMPLETE.  Only 3,377
elements with index < 32,768 exist at 64 nodes, so depth 4 is 2,792 of a
possible 4,096 -- 68% populated.

At -s 128 the prediction 1,170 was exact, at 64 AND at 128 nodes, because
depths 0..3 (585) ARE full at both scales.

CONSEQUENCE FOR THE COMMIT MESSAGE.  The whole-levels formula gives an UPPER
BOUND on what is collected, exact only while every kept level is full.  For
a deep cap on a sparse canopy the real collect is smaller than the formula
says -- which is conservative in the safe direction, but the number in the
commit message should be read as a bound, not a prediction.

This is also the argument for keying such gates to a predicted VALUE rather
than a threshold.  A "raw < 10000" check would have passed silently and I
would have reported 6,754 as if I had expected it.

3.  A DISAGREEMENT WITH relay96 THAT MATTERS MORE THAN THE 42 ms
====================================================================
relay96 (job 5331703) and relay98 (job 5333391) disagree on the SIGN of
cap-128-versus-uncapped at 64 nodes, on the same dataset and the same flags:

                         uncapped        cap 128         cap 128 is
  relay96, job 5331703    1764.8          1824.2          +59.4 WORSE
  relay98, job 5333391    1810.4          1750.2          -60.2 BETTER

Both jobs have tight, SEPARATED within-job ranges.  They are not sloppy
measurements; they disagree.

IT IS NOT THE BUILD.  I suspected 9798a06 ("avoid unnecessary reads for
fof").  It is not: that commit gates `read_velocity_and_soft` in the NCHILADA
loader only, and our 2B input (cosmo25cmb.768g2_dm.001024) is a single Tipsy
file, where the README states and the code confirms the flag has no effect.
v88 and v89main are behaviourally identical on this input.

WHAT IT IS, most likely: run-to-run allocation variance.  Neither job used
the core-thief fix (both are --cpus-per-task=14 with no FOF_HELPER_CPUS), and
the campaign's own note records a 2-4% spread for unfixed arms.  2-4% of
1780 ms is 36-71 ms, which is the size of BOTH disagreements.

WHAT THIS CORRECTS IN relay96.  Section 3 of relay96 -- both models refuted --
STANDS: it rests on within-allocation comparisons (16 nodes: uncapped best,
every cap worse; 64 nodes: cap 128 the worst arm), and relay98 reproduces the
ordering of the caps among themselves.  What is weaker than I wrote is
section 4's 64-node row.  I labelled it "a wash" and it is worse than a wash:
THE SIGN IS NOT REPRODUCIBLE ACROSS ALLOCATIONS.  The crossover is near 64
nodes, but "near" is now bounded by a systematic of the same size as the
effect, and no 64-node number should be used to place it precisely.

If the README's crossover rule was written from relay96, it is still right in
shape.  It should not be trusted to a resolution finer than ~4% at any scale
where the predicted saving is that small.

TO SETTLE IT PROPERLY: a single allocation containing uncapped and cap 128
with 5+ interleaved reps, WITH the core-thief fix applied (--core-spec=0
--cpus-per-task=16, FOF_HELPER_CPUS=0,8,...,56), which the campaign measured
at <1% spread instead of 2-4%.  I have not run it; say if it is worth a slot.
