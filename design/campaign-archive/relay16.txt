WHAT THE FORK CHANGES (read before building it -- this is where it was found)

 4. ritvikrao/lci frontier-changes @ 4ee0d15, three commits on upstream
    b8069dd.  Both it and production LCI are 2.0.0, so the diff is real and
    not a generation gap.
      production:  domain_attr->threading = FI_THREAD_SAFE, unconditional
      fork:        FI_THREAD_DOMAIN whenever multiprocess && provider is
                   cxi or unset -- which on Frontier is ALWAYS
    FI_THREAD_DOMAIN is libfabric's contract that the CALLER serialises
    access to a domain and everything under it.  The fork's OWN next commit
    (19fe6b8) adds a mutex around fi_mr_regattr/bind/enable/close with the
    comment: "FI_THREAD_DOMAIN requires caller serialisation; concurrent
    fi_mr_enable calls corrupt CXI's internal LE-append queue and cause
    cxip_mr_wait_append to spin forever."  That serialises ONE path.  Every
    send and every progress call on a shared domain is still unserialised.
    The third commit's `if (!internal_ctx) return;` guard in progress_read
    is the same story from the other end: a null completion context is what
    you get after the provider's event queue is corrupted.

 5. SEPARATE LANDMINE, same fork.  4ee0d15 adds LCI_OFI_THREADING_HINT with
    a DANGLING ELSE:  `} else` with no braces swallows the next statement,
    so setting that variable to ANY value (even an unrecognised one) also
    stops control_progress being set to FI_PROGRESS_MANUAL.  It is exactly
    the knob someone debugging stalls would reach for.  One pair of braces.
