TWO SEPARATE THINGS, and they should not be conflated:

  (a) THE ROW IMPROVED 0.429 -> 0.243 s, -43%.  But the HASH arm gets that
      too, so it is NOT the dense histogram.  It is the prefix removal:
      the truncation bug was manufacturing 262,837 phantom components, and
      more labels meant bigger maps.  With correct labels the hash path is
      simply doing less work.  Compare relay70's broken hash at 0.497 s
      against this round's correct hash at 0.243 s -- same code path, half
      the time, purely because the answer is right.

  (b) THE DENSE PATH IS A WASH AT THIS SCALE.  0.2525 s (mean of 1a/1b)
      against 0.243 s hash -- 4% apart, and 1a/1b differ from each other by
      the same amount, so it is inside run-to-run noise.  The width guard
      is doing exactly what it was built to do: at 2B the order range is
      too wide for the array, so dense takes the sort-scan path, which
      performs like the hash path.  Nothing lost, nothing gained.

So the dense histogram is now SAFE at 2B, and it is worth keeping for the
scales where the array path applies, but it should not be credited with any
of the improvement measured here.
