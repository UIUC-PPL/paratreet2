s3Shipment duration vs message bytes:
  run       calls  mean msglen  mean dur   slope        pearson r  intercept
  prewire     39    47,193 KB   164.7 ms   0.0034 us/B    0.999     +0.33 ms
  wire        41    39,608 KB   126.9 ms   0.0031 us/B    0.997     -0.60 ms

=> r=0.999 with ~ZERO intercept: message size explains essentially ALL of
   s3Shipment. No fixed per-shipment cost to amortise, no separable
   allocation-count term. A flat streaming cost of ~0.003 us/byte ~ 300 MB/s.

WHAT THE TWO CHANGES ACTUALLY BOUGHT:
  bytes/shipment (the WIRE FORMAT):  47,193 -> 39,608 KB   -16%

The offset wire format did the larger share. The arena -- the part the
addendum expected to dominate ("allocator-bound") -- bought 9%.

THE MESSAGES ARE ENORMOUS (this is the real finding):
                prewire      wire
  median        36.1 MB      27.9 MB
  p90           90.3 MB      70.1 MB
  MAX          225.9 MB     170.9 MB
  max duration   777 ms       549 ms
A single grant ships up to 226 MB and holds one helper PE for 777 ms of
uninterruptible entry time. At ~550 units/grant that is ~73 KB PER STOLEN
UNIT -- against ret_edges of only ~3,300 for the whole run.

CHARM'S UNPACK IS NOT THE COST -- IT IS ALL INSIDE THE ENTRY.
Raw records around one call (PE 1139):
  18 10611543 1139                           BEGIN_UNPACK
  19 10611544 1139                           END_UNPACK    <- 1 microsecond
  2 19 450 10611544 ... 41019920 ...         s3Shipment BEGIN, msglen 41 MB
  1  5 414 10743888 ...                      first drainForeign CREATION
Charm unpacks 41 MB in 1 us (arrives contiguous). Then 132 ms elapse INSIDE
s3Shipment before the first drainForeign is even created -- the helper's 14
PEs idle that whole window. Your "no helper PE starts until the entry ends",
now timed.

*** THIS FLIPS MY EARLIER ADVICE ON OPTION (A) ***
Item 2 above said "do not build option (A) yet". That was based on the arena
result alone. With the decomposition done, the evidence SUPPORTS (A), though
for a different reason than section 31 gave:
 - the cost is LINEAR IN BYTES WITH NO FIXED TERM, so it is perfectly
   divisible: spreading it over the helper's 14 PEs should give near-linear
   speedup of the serial head (132 ms -> ~10 ms);
 - it is NOT in charm's unpack, so it is inside code we control.

ONE DESIGN CAVEAT THE TRACE CANNOT SETTLE: s3Shipment takes a MARSHALLED
parameter (const StealShipment<Data>&), so charm's generated wrapper
deserialises the whole 41 MB BEFORE user code runs. That is inside the timed
entry but NOT deferrable by (A) as described. Splitting "marshalled
deserialise" from "tree rebuild" needs code (user bracket events, or a raw
message type). If deserialise is most of the 0.003 us/byte, then (A) must ALSO
change the entry signature to a custom message -- not merely defer the
rebuild. Worth deciding before writing (A).

ORTHOGONAL AND POSSIBLY CHEAPER: SHIP FEWER BYTES. 73 KB per stolen unit to
return ~3,300 edges is the number that stands out. Any thinning of the shipped
subtree representation multiplies directly through a cost that is 100%
byte-proportional. That is a design question for you/fable.

14. GRANT PACKING: THREE LEVERS TRIED, THREE NEGATIVES
    (jobs 5257740 / 5257769 / 5257964 -- every arm exact)
=============================================================
Your steer was right that plain m2/bytes would be shortsighted, and for a
deeper reason than tiny jobs: A UNIT'S BYTE COST IS NOT A PROPERTY OF THE
UNIT. place() dedups subtrees, so the first unit to pull one in pays and
later units sharing it cost ~nothing. Standalone per-unit density is not
even well defined. So the filter prices MARGINAL bytes, and is evaluated
BEFORE the ownership CAS -- a rejected unit stays unclaimed for the local
drain; skipping after claiming would strand it and corrupt the ledger.

  arm                       phaseB_s max  units/ship  KB/unit  work moved
  BASELINE (all off)          1.52-1.71      478-562    65-71   0.41-0.46
  GRANT_BYTES=16M             2.94/2.94          209       72   0.39
  GRANT_BYTES=8M              3.04               110       79   0.33
  DENSITY=0.25                1.88               426       --   0.59
  DENSITY=0.5                 2.07/2.17      252-258       --   0.61-0.64
  DENSITY=1.0                 2.36               140       --   0.57
  SPAN_PARTS=2                1.72/1.71      807-869    80-87   0.36-0.40
  SPAN_PARTS=4                1.85              1106       95   0.36
  SPAN=4 DENSITY=0.25         1.79               967     33.3   0.55

BASELINE WINS. Nothing beat it; SPAN_PARTS=2 tied.

 - BYTE CAP: clear loss. Halves units/grant, so doubles grant COUNT, and
   per-grant fixed cost (~125 ms, section 31) swamps the transport saving.
   DECISIVE DETAIL: 8M is WORSE than 16M. Moving FURTHER from the 16-32 MB
   cliff made it worse, so the loss is not about the cliff at all -- the
   binding cost is per-GRANT, not per-BYTE. (Knob since removed; see 16.)
 - DENSITY: succeeded at its own goal and still lost. m2/byte roughly
   doubled (217->421 vs its matched control), work moved rose to 0.55-0.64.
   It loses because as implemented it SHRINKS the grant.
 - SPANNING: works mechanically -- 542 -> 1106 units/grant, through the
   partition ceiling toward the 1792 count cap -- and does not help.

A "partition", for the record: a KD-split SPATIAL region of one process's
pool (~1/PB_PARTS of it), key-ordered internally, concatenated
costliest-first. It exists purely as a shipping granule (section 19).

TWO PREDICTIONS TESTED. Right: spanning breaks dedup locality, so bytes/unit
rose 64.9 -> 95.0. WRONG: I predicted density and spanning would FIGHT (the
filter rejects units bringing new subtrees, which is what a freshly spanned
partition offers). They COMPOSE -- filtering drains a partition sooner, which
triggers MORE spanning (1143 spans, the most of any arm), and the filter then
skims the dense units from each new region: KB/unit HALVES to 33.3 at the
best work-moved of any arm. That pair is the one worth retesting after (A).

much alone. Lever (c) -- collect from a precomputed partition manifest, or
serve orders on the donor's least-loaded PE -- attacks the term that does.

17. THE AFTERNOON IN ONE PARAGRAPH
=============================================================
Shipments are huge (40 MB median, 226 MB max, ~73 KB per stolen unit, 11 GB
per run) and their cost is ~100% byte-proportional (r=0.999 vs msglen, zero
fixed cost). Neither faster transport nor smarter selection helps: pxshm is
up to 2x SLOWER at the sizes below ours and only ~5-7% faster at ours, and
every packing lever tried was neutral-to-negative. The reason is that the
binding cost is neither transport nor selection -- it is DONOR-SIDE
COLLECTION ON THE CRITICAL PATH, which makes moving more work actively
counterproductive (r=+0.693). Along the way: a validated byte/work-per-byte
instrument, a .log.gz projections reader, an 8.8e7x measured spread in
work-per-byte, a 4.1x bandwidth cliff at 16-32 MB, the correction of a
shipped default (GRANT_M2 1e10 -> 1e11), and the finding that section 31's
"allocator-bound" diagnosis of s3Shipment was only ~15% right.

18. ADDENDUM (18:23): WHAT "COLLECTION" COSTS -- LEVER (c) IS AIMED AT THE
    WRONG HALF, AND THE DONOR'S FLATTEN IS THE BIGGEST CRITICAL-PATH TERM
=============================================================
"Collection" = s3ShipOrder: scan the partition range, CAS-claim units,
FLATTEN the deduplicated subtrees, send. So: selecting AND packing.

s3ShipOrder duration distribution (projections traces):
              calls    p50       p90      p99      max     total
  prewire      244   0.013 ms  101.2 ms  540 ms  858 ms   6.93 s
  wire         232   0.015 ms  102.6 ms  353 ms  667 ms   6.67 s

THE MEDIAN CALL IS 13 MICROSECONDS. ~84% of calls scan, find nothing
claimable, return free. ALL the cost is in the ~16% that build a shipment.
(The roster already hinted at this: 4,569 order calls served 473 ships.)

PER SHIPMENT:
  donor flatten  (s3ShipOrder)  ~178 ms   ON THE STRAGGLER, CRITICAL PATH
  helper rebuild (s3Shipment)   ~165 ms   on an idle helper PE
  transit                        ~27 ms   fabric

*** THE DONOR'S FLATTEN IS THE LARGEST CRITICAL-PATH COST PER GRANT, AND IT
    IS BIGGER THAN THE HELPER REBUILD THAT OPTION (A) TARGETS. *** This is
the mechanism behind section 15's r=+0.693: each extra grant adds ~178 ms to
the hottest process.

SO LEVER (c) AS WRITTEN DOES NOT FIT THE MEASUREMENT:
 - "precomputed partition manifest instead of per-unit scan+CAS" attacks the
   SCAN, which costs 13 us. Saves nothing.
 - "service orders on the donor's least-loaded PE" moves the flatten, but the
   straggler's 14 PEs are all busy draining -- it relocates cost inside a
   saturated process.

WHAT THE DATA SUPPORTS INSTEAD: PRECOMPUTE THE FLATTEN, not the manifest.
Partitions are known before any order arrives, so their deduplicated subtrees
can be flattened ONCE -- during idle time, or spread across PEs -- leaving
s3ShipOrder as little more than handing over a prepared blob. That is option
(A)'s trick applied to the DONOR side.

REVISED LEVER RANKING:
  1. Precompute/parallelise the DONOR-side flatten (revision of 31(c)):
     ~178 ms on the critical path, the term that correlates with the straggler.
  2. Option (A) lazy/parallel helper rebuild: ~165 ms, but paid by idle PEs.
     Still worth having (serial head + one-outstanding-shipment limit).
  3. The packing knobs: retest only after 1 and 2 change per-grant cost.

Caveat: 39-41 shipments in a 224-PE subset is small n; the 13 us vs 100+ ms
separation is not subtle, but per-shipment averages carry small-sample error.

19. CORRECTION (18:31) -- KALE'S CPU-SECOND OBJECTION IS RIGHT.
    SECTIONS 15 AND 18 ARE PARTLY RETRACTED. READ THIS WITH THEM.
=============================================================
Kale: "the collection cost is borne by 1 PE, but the shipment is worked on by
14 PEs on the recipient -- so in CPU seconds it is a net gain for the donor,
or at least the loss is 1/14th." Correct on both counts.

PER SHIPMENT (projections @1e11, 39 shipments in the traced subset):
    donor flatten  (s3ShipOrder)   0.178 PE-s   on 1 PE
    helper rebuild (s3Shipment)    0.165 PE-s   on 1 PE
    stolen work    (drainForeign)  0.964 PE-s   spread over ~13.7 PEs

  => donor pays 0.178 PE-s to offload 0.964 PE-s: a 1 : 5.4 NET GAIN.
  => donor wall cost is 177.7 ms OF ONE PE = 12.7 ms process-equivalent,
     NOT the 178 ms of critical path section 18 implied.
  (Section 18 also used the wrong drainForeign figure, 69.70 s from the
   sum-detail run instead of 37.59 s from the projections trace, which
   inflated the ratio to 1:10.1. Corrected here.)

Refinement worth keeping: PE-SECONDS ARE NOT FUNGIBLE. The donor spends
SCARCE capacity (its 14 PEs are the busy ones -- that is what makes it the
straggler) to offload onto FREE capacity (helpers are idle by construction).
Trading scarce for free at 1:5.4 is unambiguously good.

*** AND THE REAL PREDICTOR IS GRANT COUNT, NOT WORK MOVED ***
Over the same 14 no-byte-cap arms:
    grant COUNT vs phaseB_s max : r = +0.919
    work MOVED  vs phaseB_s max : r = +0.693
    grant COUNT vs work MOVED   : r = +0.829   <- the confound
Section 15's claim was picking up grant count through that confound: the
density arms moved more work BY MAKING 3-5x MORE GRANTS (1082-1503 vs ~315
at baseline). Section 15 is RETRACTED AS STATED -- its data stands, its
explanation does not.

REVISED MECHANISM: declining marginal VALUE at fixed marginal COST. Each
grant is individually a 1:5.4 win, but early grants take work off the
critical path while later ones increasingly ship work that was not binding,
at the same fixed ~178 PE-ms to their donor. Past some count the marginal
grant is net negative. The density arms ran deep into that region: most work
moved, most grants, worst straggler.

LEVER RANKING (sharpened, not overturned):
  1. Precompute/parallelise the DONOR-side flatten -- justification is now
     "RAISE THE BREAK-EVEN GRANT COUNT", not "the donor pays too much".
  2. Option (A), helper rebuild: 0.165 PE-s on IDLE PEs, so cheap in CPU
     terms already; its value is the serial head and the one-outstanding-
     shipment-per-helper limit, not CPU seconds.
  3. Fewer, larger grants remain right AT TODAY'S COSTS -- which is why
     baseline beat every packing lever and the byte cap lost worst.

HONESTY NOTE: two of my explanations were retracted this afternoon -- the
log(units/ship) correlation (section 14) and work-moved (this section). Both
were correlations across heterogeneous arms where mechanisms co-vary. The
per-grant PE-second accounting above is the first account grounded in
measured costs rather than a fitted trend; build on that one.

21. MARSHAL vs SEND (job 5260928, both exact) -- KALE'S CONTIGUITY OBJECTION
    WAS LOAD-BEARING. BUILD ARENA-FLATTEN FIRST.
=============================================================
Kale: "even with post API you need a contiguous message at the source -- what
is marshal? didn't the flatten do it?"

FLATTEN DID HALF. b797e73 gave the wire FORMAT (offset-based nodes, no
pointers to fix up -- the hard prerequisite). It did NOT give contiguity: a
shipment is vector<StealTree>, each holding two vectors, plus unit_pairs.
MARSHAL is charm's sizer+toMem pass that GATHERS those into one buffer.

MEASURED (timed PUP::sizer walks what toMem walks, without copying):
  s3ShipOrder           134.9 ms/grant  (17.1 ms is measurement scaffolding)
    flatten              30.3 ms         22.5%
    marshal+send         87.1 ms         64.5%
      sizer walk         17.1 ms
    TREES PER SHIPMENT  189.1  =>  379 SEPARATE VECTORS TO GATHER

Net of the scaffolding, per grant:
    flatten (tree walk)   ~30 ms   26%   <- arena flatten helps
    MARSHAL GATHER        ~34 ms   29%   <- arena flatten REMOVES
    SEND (donor blocked)  ~53 ms   45%   <- post API removes
    total                ~117 ms

189 trees per shipment is why a pass that COPIES NOTHING still costs 17 ms.

BUILD ORDER -- ARENA-FLATTEN FIRST:
  1. it removes the ~34 ms gather outright;
  2. it needs no new charm API;
  3. it is the PREREQUISITE for the post API, which needs a registered
     contiguous source buffer -- nothing produces one until marshal does.
Post API then takes the ~53 ms send block. Together ~74% of donor collection.

HONESTY ON THE SEND NUMBER: send~53 ms assumes pack ~ 2x sizer. If the copy
is cheap, pack~17 and send~70; if pack~3x sizer, send~36. SEND IS SOMEWHERE
IN 36-70 ms; narrowing it needs a timer inside charm's generated marshalling.
The gather figure (17 ms of pure traversal over 379 vectors) is MEASURED.

The extra sizer pass inflates s3ShipOrder in this run only (134.9 vs ~117).
It is scaffolding, flagged in the code, and must come out before merge.

*** MY TWO VACUOUS VALIDATIONS -- THE LESSON OF THE NIGHT ***
I twice reported evidence that could not have caught this failure:
 1. "All four 10k gates passed, including zc-loopback." AT 10k S3 SHIPS

Both ran at a scale where the code under test does not execute. Same failure
mode as the earlier retractions, one level down: there I trusted correlations
whose mechanisms co-varied; here I trusted tests whose scale excluded the
mechanism. The number was real; the inference was not.
